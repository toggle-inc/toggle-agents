# 共通経費ランタイム

このフォルダの `runtime/` が業務処理の本体です。SA・Buzz・Codexの指示をここへ複製せず、
同じ定義・同じ本体へ接続する入口を用意します。kickflowや別のエージェントは移植対象ではありません。

## 機能の対応

| 既存の経費アシスタントの機能 | 共通実装 | 公開テストでの検証 |
|---|---|---|
| 本人のMF OAuth連携・更新 | `MFClient` / `mf_auth_url` / `mf_auth_complete` | 模擬HTTP、state・本人・期限・秘密の非表示 |
| 会社選択、期間内の明細、申請・事前申請の参照 | `mf_offices` / `mf_list_transactions` / `mf_list_reports` | 合成データ、会社の曖昧性・申請済み・取得上限 |
| 科目ID・プロジェクト・過去の書式 | `mf_known_items` | 合成データ |
| 支払先・インボイス番号・毎月の出し忘れ | `mf_payee_memory` | 合成データ、会社間の混線防止 |
| iCalの読み取り・繰り返し予定 | `Calendar` / `calendar_events` | 合成ICS、時差・繰り返し・中止 |
| 運賃検索・経路ごとの金額・出典 | `Fares` / `fare_lookup` | 合成HTML。広告の金額を運賃にしない |
| 社内規則・非公開の補足資料 | `PrivatePolicy` / `check_rules` / `read_reference` | 非公開設定のハッシュ固定、参照範囲検証 |
| 添付画像/PDF、過去の領収書 | `Receipts` / `fetch_attachment` / `mf_get_receipt` | 合成バイナリ、形式・所有者・パス制限 |
| 明細作成・修正・削除・領収書OCR | 元と同名の4ツール | 模擬MF。承認、変更検知、再起動後の再送防止 |
| 会社・金額・科目・出席者・出典付きの案 | `form` / プレビュー | 合成フォーム。推測・必須不足では登録しない |
| 定期区間・拠点・書式の教え、廃止 | `State` / `expense_context` / `propose_teaching` | 本人別の提案・承認・履歴 |
| 未来の予定の保留、期日後の再確認 | `State` のpending | 合成時計、完了状態 |
| 能力カード、週1回までの提案 | `expense_context` / `State` | 設定と実機成功を区別、頻度・状況制限 |

業務ツール16個を共通サービスから呼べます。**実アカウントでの全機能成功を示す表ではありません。**
公開テストは模擬サービスのみを使います。実接続の結果は各利用環境で別管理し、実データをGitへ含めません。
申請書の作成・提出を代行する機能は、元の経費アシスタントと同様に提供しません。

## 単独セットアップと検証

```sh
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m unittest discover -s . -p 'test_*.py' -v
```

第三者依存はこのフォルダの `requirements.txt` に固定しています。
本体・テスト・依存宣言・配置手順は、このフォルダだけで完結します。

## ローカルMCPの入口

`mcp_server.py` はstdio専用です。匿名HTTPサーバーやトンネルは開きません。

```sh
.venv/bin/python mcp_server.py
```

信頼済みの起動ホストが、本人専用の設定を環境変数または外部のprivate profileから渡します。
設定値・トークン・iCal URL・規則ファイル・社内資料・状態DBはGitへ保存しません。

- `EXPENSE_OWNER_KEY`：起動ホストが検証した本人の識別。本文やモデルが指定する本人ではない。
- `EXPENSE_STATE_ROOT`：公開フォルダ外の私有データ保存先。資格情報・承認台帳・記憶・領収書を保存。
- `MF_CLIENT_ID` / `MF_CLIENT_SECRET` / 必要なら `MF_REDIRECT_URI`：管理者が用意するアプリ設定。
  本人ごとのOAuth承認が必要な点は維持し、共有管理者トークンで代替可能とは仮定しない。
- `KEIHI_ICAL_URL`：本人の非公開iCal URL。
- `EXPENSE_ATTACHMENT_HOSTS`：信頼済み入口が使う添付先の厳密な許可ホスト。ローカル・metadataへの取得は禁止。
- `EXPENSE_PRIVATE_POLICY` / `EXPENSE_POLICY_SHA256`：認可済み規則のPythonモジュールと固定SHA-256。
  既存の規則と同じ `check(..., position=...)` 契約を利用できる。コード実行権限がある管理者だけが設定する。
- `KEIHI_POSITION`：信頼済みの役職設定。モデルが指定しない。
- `EXPENSE_PRIVATE_REFS`：認可済みの補足資料ルート。未設定を「規則点検成功」と扱わない。

`--factory /private/path/profile.py` は管理者が用意する `create_service()` の注入に使います。
**1プロセス＝本人1人のstdioプロファイルです。** 同じプロセスを複数社員へ無認証公開してはいけません。
共有サーバーでは、認証済みリクエストから本人別のサービスを選択する基盤側の実装が必要です。

## 承認とカードの入口契約

### 配送判断の正本

配送ルールはこのエージェントの `delivery.json` が正本です。SA/Buzz等がエージェント名を見て
独自に「経費だからDM」と判断する設計にはしません。各サービスの用語・私的会話の種類・論理的接続役割も
`platform_bindings` に保持します。接続ID・実宛先・資格情報は信頼済みホストが環境ごとに束縛します。
記載のcapabilityは要求する機能の識別子であり、実在のAPI名や接続済みの証明ではありません。

配置時に契約とSHA256を指示へ組み込み、同じファイルと `runtime/delivery.py` も成果物に含めます。
静的な `delivery_contract` ツールは個人データを取得せず契約を返します。
`resolve_binding` は正本から配送先種別を選び、非公開配送の機能・保証が不足する場合は保留を返します。
ホストが渡す検証済み能力をモデルの自己申告で代替してはいけません。

方針は「全結果を認証済み依頼者だけへ、起点には固定受付のみ」です。中間結果・ツール結果・エラー・
添付・進捗・完了サマリーも対象です。プラットフォーム側には、認証済み依頼者と非公開宛先の解決・検証、
契約どおりの配送、重複防止、配送不能時の保留という汎用アダプター機能が必要です。
公開チャンネルへの本文ストリーミングや、DM失敗時の公開フォールバックは認めません。

**この正本追加だけで既存のSA/Buzz配送処理や公開済みEngine版が変わるわけではありません。**
アダプターが公開版と同じ契約を取得・検証して個人データの配送前に適用する結合検証は別途必要です。
プラットフォームごとの実配送・社員間の分離が未検証なら、本番適用済みとは報告しません。

`confirm=false` はプレビューID・内容ダイジェスト・有効期限とフォームを返します。
入口は本人に会社・対象・全項目・警告を示し、認証済みの本人操作だけを
`State.approve(preview_id, expected_digest)` へ変換します。このメソッドはMCPへ公開しません。
本人の記憶の確定・廃止・保留完了も、信頼済み入口が `accept_fact` / `retire_fact` / `complete_pending` で行います。

モデルはこれらを直接呼べません。「OK」やボタンの意味の本人性・会話・対象・版への束縛は入口の責務です。
未実装の入口でAIが自分に承認を発行する代替処理を作ってはいけません。
週次提案の `mark_suggestion` は実際に配送した入口が記録し、見回り・急ぎ・失敗中を除外します。
同時に複数の入口から送る場合の配送排他は入口側で保証する必要があります。

Buzzの読み・リアクション・ローカルファイル表示は、フォーム・本人操作・MCPリソースへ分離しました。
表示を表やカードにするSA側の実装、リアクションと対象を結びつけるBuzz側の実装は別の入口作業です。
MCP対応クライアントは `resource_uri` から本人の画像/PDFを読み取れます。

## 配置と未完了事項

### 既存の本人用Buzz設定へ接続する場合

新しいアプリキーやトークンをチャットへ貼り直す必要はありません。
信頼済みのローカル設定手順で、既存の本人用設定への参照を作成できます。

```sh
.venv/bin/python connect.py setup --legacy-env /private/expense/.env --directory /private/common-expense
.venv/bin/python connect.py check --profile /private/common-expense/connection.json --date YYYY-MM-DD --fare-from 東京 --fare-to 品川
.venv/bin/python connect.py serve --profile /private/common-expense/connection.json
```

`.env` は実行・変数展開せずデータとして読みます。接続プロファイルにはファイル参照と本人への束縛だけを保存し、
キー・トークン・カレンダーURLのコピーは保存しません。元の認証ファイルを共用し、必要なOAuth更新結果は
その元ファイルへ原子的に反映するため、旧ランタイムの認証情報だけが古くなる状態を避けます。
複数の新ランタイムと旧ランタイムで同時に認証更新する場合の排他は別途必要です。
既存設定の持ち主と参照先は、初期設定を行う信頼済みホストが確認します。パスのハッシュは本人認証の署名ではありません。

認可済み補足資料のキャッシュを使う場合は、私有接続プロファイルの `private_references` に
公開フォルダ外の `index.md` を持つ参照ルートを指定できます。本文は公開定義へ入れません。
原本の版・内容ハッシュ・取得日を保存し、Markdown変換の未対応ブロックがある場合は警告と原本データも保持します。
キャッシュを最新の制度の証明とせず、必要な箇所は元の資料と照合します。

接続は既定で**読み取り専用**です。承認台帳に記録があっても、実行プロファイルが許可しなければ書き込みません。
本人から書き込み能力の有効化を依頼された場合、信頼済みのローカル管理操作で切り替えます。

```sh
.venv/bin/python connect.py writes --profile /private/common-expense/connection.json --enable
# 再び読み取り専用へ戻す場合は --disable
```

既存のstdioサーバーは再起動が必要です。この操作自体はMFへ書き込まず、個々の経費の承認も発行しません。
本人・会社・対象・全内容・期限に束縛した承認は引き続き必須です。承認機能や能力切り替えをモデルの道具へ公開しません。
実書き込みの検証には、本人が会社・利用日・金額・内容等を確認した実在の経費を使います。
架空の経費を本番MFへ登録したり、既存の明細を無断で変更・削除したりして疎通を確認しません。

### 同じ領収書の二重登録防止

明細作成とMF OCRアップロードは、本人専用の状態DBで領収書の内容ハッシュを共有します。
確認画面の作り直し・別名の添付参照・会社変更・作成/OCRの切替でも、同一バイト列の
領収書から新しい経費を重ねて作りません。照合の予約と実行開始は同じSQLiteトランザクションで
記録し、別プロセス・再起動後も保持します。未承認・期限切れの試みは予約を消費しません。
元の承認IDの再送は保存済み結果だけを返し、結果不明なら新しい承認IDでも実行を保留します。

これはこの本体・同じ本人用状態DBを通した操作の防止です。MFで手動登録済みの領収書、
導入前の処理、別の状態DB、画像の再圧縮・切抜きなどバイト列が異なる再撮影は自動検知しません。
登録前には既存明細を本人と確認します。OCR受付を完了と見なさず、実MFで明細を照合します。
同じ領収書の分割精算や処理結果不明の解除は、自動実行せず人間が照合する別手続きが必要です。

### MF登録後の読み戻し

作成・修正の応答の明細IDを使い、同じ本人・会社の `/me/ex_transactions/{id}` をGETします。
日付・金額・内容・科目ID・メモ・事前申請番号・プロジェクト/部門ID・登録番号のうち、
今回送った項目を比較します。`verified_fields` は実際に比較した項目の一覧です。
空文字での任意項目削除は明示的なnullも許容しますが、フィールド欠落では照合済みとしません。
領収書添付を送った場合は `mf_file` の存在も確認します（画像バイト列の一致証明ではありません）。
出席者など上記にない入れ子項目を、この読戻しで検証済みとは扱いません。

成功は `readback_verified=true` とともに返します。未反映・不一致・読取不能は結果不明として保留し、
再送せず本人に実明細の照合を求めます。MFのOCR完了確認はこの処理とは別で、受付だけでは成功にしません。
API形状は [MF公式API](https://expense.moneyforward.com/api/index.html) で確認しています。

SAの本人確認画面との信頼済み接続は [SA_APPROVAL.md](SA_APPROVAL.md) を参照してください。
アダプターの合成検証と、実行ホスト・本人認証・サービス資格情報の実接続は別段階です。

### MF OCRの状態追跡

読み取り専用の追加ツール `mf_receipt_status(upload_preview_id)` は、本人用台帳に保存した
承認済みアップロードの応答だけを起点に、同じ本人・会社の明細を照合する。
MFの返した `ex_transactions[].id` がある場合は各明細をGETし、`mf_files[].id` だけの
場合はそのファイルIDが一致する明細だけを一覧から選ぶ。日付・金額による推測はしない。
一覧を取得し切れない場合や参照先が矛盾する場合も、成功とは扱わない。

`automatic_status=input_done` かつ全ての関連先が揃い、エラー・警告がない場合のみ
`ocr_complete=true` とする。処理中・関連明細未生成・キャンセル・未知の状態・結果不明・
相関IDなしは別の状態として返す。認識した登録番号も本人が確認し、追加・変更は再プレビューと承認を行う。
このツールはアップロード・書き込み・承認を実行しない。本人別能力は既存の `mf:read` に束縛する。
公式仕様の根拠は `upload_receipt` の返却IDと `ExTransaction.automatic_status`。

現時点で確認したEngineの外部MCP経路は結果をテキストとして扱うため、MCP画像リソースが
あるだけでモデルに画像を読ませられるとは仮定しない。まず既存のMF OCR経路を利用する。
アップロード自体が明細を作る可能性のある書き込みなので、必ず送信前に本人承認を得る。
OCRによる明細作成前に画像から候補を読む経路は、別途画像入力の実機検証が必要。

`check` はMFの会社・明細・申請一覧、カレンダー、規則を読み取り、指定した場合だけ運賃を調べます。
出力は成功可否と件数だけで、明細本文・予定本文・認証情報・非公開URLを表示しません。
補足資料の未設定や実添付ファイルの未検証を、成功とまとめません。
実MFへの作成・更新・削除・OCRは、この接続検査では実行しません。

これはローカルMCPの実接続です。EngineやSAへ自動的に登録したり、個人の認証情報をクラウドへ転送したりしません。

### Engineから本人専用ツールを利用する場合（テナント10限定検証）

`engine_mcp.py` は同じサービスを認証付きStreamable HTTP MCPとして提供します。
秘密・領収書・承認台帳は実行ホストの非公開領域に残します。新しい業務実装は複製しません。

```sh
.venv/bin/python engine_mcp.py issue-key --profile /private/common-expense/connection.json --key-file /private/common-expense/engine-key.json
.venv/bin/python engine_mcp.py serve --profile /private/common-expense/connection.json --key-file /private/common-expense/engine-key.json --public-host YOUR_EXACT_HTTPS_HOST
```

- ホストはloopbackにだけbindし、別途設定したHTTPS入口から到達させます。匿名リクエストはMCP処理前に401、期限切れ・削除・本人不一致のキーも拒否します。
- キーはテナント10・本人・最大24時間に束縛し、公開Git外へ600で保存します。再発行時に既存キーを上書きしません。
- Engineのテナント10にAPI Key方式の外部MCP接続を作り、`Authorization: Bearer <接続キー>` を暗号化保存します。MFキー・OAuthトークン・iCal URLはEngineへコピーしません。
- このキーは本人の道具を呼べる**接続権限**であり、リクエストごとの社員認証ではありません。信頼済み管理者の本人専用テストに限定します。複数社員・一般のSA入口へ共有してはいけません。
- 接続IDを指定して経費アシスタントをDRAFT配置し、Engine Playgroundで検証します。作成・更新・削除・OCRの実行は個別承認なしには許可しません。
- 一時HTTPSトンネルはPCとプロセスが動いている間だけ有効です。24時間後も使える常設クラウド配置や、SAからの本人確認付き承認操作を実装済みとは扱いません。
- ソース同梱、接続登録、Engine実呼び出し成功、公開／各入口への反映はそれぞれ別に確認します。

`deploy.py` は定義とランタイムソースを同じ成果物へ収録します。
検証済みの本人専用MCP接続をEngineに登録した後、`--connection-id <接続ID>` で生成物だけへ束縛できます。
正本の `conn_ids` は空のままです。接続を指定しないDRAFTに業務ツールが付いたとは扱いません。
このコード追加だけでHTTPサービス・Engine接続・従業員の認証・SAの@入口を作成することはありません。

残る受入検証は、本人の接続を安全に設定し、同じ配置版をSA/Buzz/Codexから呼び、
承認カード→実行→照合が入口をまたいでも正しく働くことです。実書き込みは対象と内容を承認してから行います。
MFの公式APIが対応する範囲、運賃サイトのHTMLやOAuthの運用要件は、実接続前にも確認してください。
