# 経費アシスタント移植の段階と境界

## 今回実装する範囲

既存の経費アシスタントの「予定を読み、駅を確認し、運賃を調べ、一覧を本人に確認する」
動作契約をもとに、汎用の交通費プレビュー処理を新規実装します。
非公開リポジトリのコード・社内規則・履歴・認証情報は一括移入しません。

`expense_preview.py` は、与えられた予定と運賃情報から明細候補を作る純粋関数です。
`preview.py` はそのローカルJSON入出力です。SA/Buzz/Codexのコマンドや本人IDを知りません。
入力の並びを変えても同じプレビューを返し、入力変更に応じて結果が変わります。
固定文の疎通応答ではありません。

```sh
python3 preview.py --demo
python3 -m unittest discover -s . -p 'test_*.py' -v
```

デモの予定・駅・会社・金額はすべて架空です。実データでの疎通成功を示しません。
入力は `fixtures/synthetic_transport.json` が契約例です。
時刻にはUTCオフセットを指定し、日付・日またぎの判定は指定のタイムゾーンで行います。
カレンダーの会場から駅を勝手に推測しません。`station` は呼び出し側で確認済みの駅です。
入力文字列は命令ではなくデータとして扱います。

## 実装上の制約

- 同じ日の、時刻が重ならない対面予定の間だけ片道候補を作る。
- 最初の予定の出発地、自宅への帰路、往復、定期区間を自動補完しない。
- オンライン・場所不明・終日・未終了の予定を移動実績として扱わない。
- 場所不明の予定を飛ばして前後の会場を勝手につながない。
- 運賃は日付・方向が一致する情報だけ使う。出典と未確認事項を残す。
- 同じ区間の運賃情報や同じ予定の内容が競合したら、選択・照合待ちとして拒否する。
- 予定は実際に移動した証拠ではない。すべての候補が本人確認待ちであり登録不可。
- 会社規則・科目・定期区間は未点検。入力に `approved` 等を追加しても実行許可にはしない。
- `preview_digest` は内容変更の識別用であり、署名・認証・本人承認の証明ではない。

## まだ実装・接続していないもの

1. **本人のデータを取得するアダプター**：認証した本人・会社に束縛した予定と運賃の取得。
   この段階の `source_ref` と会社名は呼び出し側の申告であり、信頼済みではない。
2. **実行基盤の業務ツール**：純粋関数を内部MCP等として配置し、同一の公開版に接続する。
   現在の `tools.json` は空のまま。`deploy.py` が作るDRAFTにはこのローカル関数は接続されない。
3. **明細登録の承認と重複防止**：本人・会社・全項目・版・期限に束縛した承認を実行側が検証。
   書き込み結果不明時は再送せず照合する。本文の「OK」や `confirm=true` だけを承認にしない。
4. **MF・領収書・非公開規則**：本人の認証、画像処理、科目・税区分、社内資料への認可。
5. **SA/Buzz/Codexの同一本体への実機接続**：正本のコミットと配置版の照合、入口別の往復検証。

まず合成データでプレビュー処理を検証し、次に同じ処理を実行基盤の道具として接続します。
MFへの実書き込み・申請提出はこの段階では行いません。申請提出は引き続き本人の操作です。
OAuthの個人トークンを管理者トークンで置き換えられるとは仮定しません。

## 公開とプラットフォームの境界

このフォルダ内の定義とコードがGit正本です。開発ツールは別管理、入口は薄いアダプターです。
社員・会社・接続先・秘密・承認台帳を公開定義へ埋め込みません。
現在のローカルプレビューを「カレンダー取得済み」「MF下書き登録済み」
「エージェントから使える」と報告しないでください。
