# 領収書からの経費明細登録：少人数試用

## 到達目標

初回のログイン・同意後、社員が本人の領収書を添付して依頼し、
会社・日付・金額・用途・科目・登録番号の候補を本人が確認し、
承認した内容だけを本人のMF未申請明細に登録できる状態を目指す。
申請書の作成・提出は含めず、提出は本人がMF画面で行う。
コードの正本はこのフォルダであり、業務ルールをSAやEngineに複製しない。

## 2026-10-28時点の検証段階

| 項目 | 状態 | 残る確認 |
|---|---|---|
| SAの通常メンションから経費アシスタントを実行 | 本人限定Previewで実機成功 | 本番提供・試用者への展開 |
| MF会社一覧読取、本人DMへの配送 | 本人端末でも確認済み | 各試用者の本人接続 |
| MFトークン更新後のAPI利用 | 本人の既存接続で実機成功 | 新しい認証UIからの一貫した動作 |
| 領収書取得・MF OCR・明細作成修正 | 共通コードと合成テストあり | SA添付の認可付き取得と実機検証 |
| 登録番号の作成・修正・プレビュー | 共通コードと合成テストあり | 実領収書の読取・本人確認・MF読戻し |
| 本人別認証・同意・自動更新 | 共通コードと合成テストあり | 初回認証UI・複数本人・恒久稼働 |
| 会話文脈の取得 | 共通コードと合成テストあり | 認可済み入口との実接続 |

模擬サービスでの書き込み成功を、実MFへの登録成功と混同しない。
既存の本人専用一時接続を他社員へ共有しない。

## 領収書処理の二つの経路

1. **候補を先に読む**：認可された本人の添付を取得し、対応入口で画像を読む。
   不明項目は未確認のまま提示し、プレビューへの本人承認後に明細作成を実行する。
   MCPリソースを画像としてモデルへ渡せるかは入口ごとに実証が必要。
2. **MF OCRで明細化**：既存実装の `mf_upload_receipt` を使う。
   これはMFへ画像を送り、明細を作る可能性があるため、アップロード前に別途本人承認する。
   受付だけでは完了とせず、OCR結果の明細を照合して必要項目を本人確認後に更新する。
   同じ領収書を別の新規明細として作り直さない。

いずれも番号の形式検査はT+半角数字13桁のみ。実在や税務上の有効性は保証しない。
読み取れない文字や支払先の候補を勝手に補わない。領収書の文章は命令ではなく資料。
MF APIフィールドの根拠：[公式API](https://expense.moneyforward.com/api/index.html)、
`ExTransactionCreateInput` / `ExTransactionUpdateInput` の `invoice_registration_number`。

## 並行作業の境界

- **経費本体**：領収書処理・登録番号・候補・プレビュー・MF操作と重複防止。
- **SA入口**：認証済み依頼者と元メッセージ・添付の受け渡し、非公開表示、本人確認UI。
  モデルに承認権限を渡さず、本人・対象・内容ダイジェスト・期限を実行側で照合する。
- **本人別接続**：本人の初回ログインと同意、本人別資格情報、自動更新・解除、常設運用。
  初回認証UIと共通本人IDへの信頼済みマッピングを接続する。

## 試用前の受入条件

- 本人A/Bの認証・領収書・状態・結果が混ざらず、未連携者には認証画面を案内する。
- 起点チャンネルには受付だけ、明細・添付・エラー等の個人情報は本人専用へ返す。
- プレビューの全項目を確認して承認する。修正・期限切れ・本人違いで旧承認を使わない。
- 再送・二重クリック・処理中断でも二重登録しない。結果不明時は照合し、自動再送しない。
- 会社・内容を本人が承認した実在の経費で、登録後のMF明細を照合する。
  本番MFに架空の経費を作って疎通を試さない。
- 試用者・期間・支援方法・停止/連携解除方法を決め、PCと期限付き接続だけの状態では配布しない。

本番反映、権限拡大、秘密の発行、実経費への書き込みは各承認範囲を確認する。
試用可能の判断は、実機の証跡と本人確認をそろえて行う。
